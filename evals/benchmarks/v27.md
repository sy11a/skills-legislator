## Addendum, 2026-09-22 — the number is assigned, and the edition carries a second half

**`skill/VERSION` is `27` from BL-397's merge.** The ruling this record left to the operator —
*"the operator rules on the number"* — was put as a recommendation and taken: **27 carries both
halves.** L-1's law change and BL-397's engine change are each unreleased and no repository has
either, so splitting them across two editions would make every governed repository take two
upgrades for one week's work; edition numbers are assigned at merge and never reserved, which is
the rule L-1's own claim on 25 taught.

**The second half, and how it is measured.** BL-397 makes a retirement and the declaration that
names it one act: `apply` rewrites a repository's declaration homes from `python3 <retired> <job>`
to `legislator <job>`, refuses at exit 4 on a shape it cannot rewrite with nothing written, and
counts rather than rewrites the records. It is measured by the .NET suite (762 tests, 57 of them this case's) and by a dry run of a locally built `27.0.0` binary (no 27 is published yet — see below) over scratch copies of all four repositories
the change exists for — clerk, debrief, dev-flow and foundry — which move **eleven declarations in seven files** between them — foundry's `tools/gate.sh` and the
`.claude/rules/verification.md` rows it is reconciled against in the same run — and over all eight
scenarios of this repository's own e2e corpus, `upgrade` and `upgrade-drop-stack` included, which
retire a rule file and a whole stack.

**What this addendum does not claim, and what it owes.** The figures above (211/214, the mutation
pass) are L-1's, measured with the `26.0.0` arm, and BL-397 does not re-measure them: its change is
in the engine's `apply` job. **An earlier draft of this addendum said the e2e benchmark
"exercises [that job] through the skill rather than asserting on" it, which is false** —
`evals/grade.py` asserts `retired_rule_deleted` and `dropped_stack_files_deleted` directly, and
the first version of this change turned both red by refusing every upgrade that retires a rule.
All eight scenarios are run here and pass; what is not re-measured is the 211/214 figure itself. Owed before a repository takes 27:

1. **A published `27.0.0` binary, with its digest in `skill/assets/release/release.json`.** Until
   there is one, `python3 evals/check_engine.py` reports `[arm-integrity] the installed arm reports
   26.0.0 where this edition pins 27.0.0` on any host whose installed arm is 26 — correctly. That
   is the release's act, not this case's, and the finding is the check working.
2. **The e2e benchmark re-run against that arm**, so this record's numbers describe the edition it
   names rather than the one before it.

**The standing order in `sy11a/Architector#448`** — *no governed repository takes edition 26* — is
answered by this edition rather than by 26: 27 is the first edition whose upgrade moves the
declaration with the retirement, so the order lifts per repository as each takes 27, and each will

## Harness note: hand-run `grade.py` overwrites the recorded verdict

`evals/grade.py <ws> <scenario>` (the CLI form) writes `grading.json`
**unconditionally on every invocation**, including from a checkout other than
the one that produced the run. Grading `legacy-migration`/`restructure` by
hand from the `origin/master` worktree for the comparison above briefly
overwrote both scenarios' recorded `grading.json` with master-vintage
verdicts; caught before `evals/mutate.py`'s substrate-validation step (which
compares the recorded file against a fresh in-process re-grade) flagged
`legacy-migration` `UNUSABLE`, and repaired by re-grading once more from this
branch. The mutation pass afterward is the one that counts (214/214 killed,
0 unusable) and reflects the corrected, branch-consistent files.
