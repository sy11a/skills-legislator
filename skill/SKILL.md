# Legislator

Run this procedure against the **current working directory** (the target project repo). Never write outside it. Never commit — leave the diff for the user to review. `<skill-path>` in the commands below means this skill's install directory (typically `~/.claude/skills/legislator` or `~/.config/opencode/skills/legislator`, a symlink to the skill package).

If the user's request is to **audit** or health-check the existing AI layer (no scaffolding or upgrading intent), do not run Steps 0–7 — follow the **Audit — read-only health check** section near the end of this file instead. If it is to **restructure**, repair, or reorganize the AI layer, follow the **Restructure — approval-gated repair** section at the end of this file instead.

## Step 0 — Preconditions

1. Confirm the current directory looks like a project root (has a `.git` directory, or the user has explicitly confirmed this directory is the target). If neither is true, ask the user to confirm before proceeding.
2. Run `git status --porcelain`. If it reports anything, warn the user that uncommitted changes exist and ask whether to proceed (a run's diff would mix with their changes) before continuing.

## Step 1 — Detect state

The repo's entry document is **`AGENTS.md`** (the constitution — `docs/ai/rules/**` @ VERSION — is delivered by Step 3, not this file). `CLAUDE.md` is a compatibility symlink to it (Claude Code reads `CLAUDE.md`; opencode reads `AGENTS.md` — both resolve to one source of truth). Check, in this order:

1. Does `docs/ai/manifest.json` exist? → **upgrade** mode. Read it for the previously applied `legislatorVersion`, the stack subscription (`stacks`; a legacy manifest may carry the same field as `profiles` — treat it as the subscription and rewrite it as `stacks` this run), `keep`, and `ownedFiles`.
2. Else, does `AGENTS.md` exist at the repo root? → **legacy migration** mode.
3. Else, does `CLAUDE.md` exist at the repo root as a real file (not a symlink)? → **legacy migration** mode (a pre-v14 repo whose canonical file is `CLAUDE.md`; Step 5 renames it to `AGENTS.md` and replaces it with the symlink).
4. Else → **fresh scaffold** mode.

**Edge case — manifest missing but the entry document already carries the import block:** before treating a manifest-less repo as legacy migration, check whether `AGENTS.md` (or, in the pre-v14 case, the real `CLAUDE.md`) already contains the `@docs/ai/rules/core/okf.md` import line. If it does, the repo was already legislated at some point and the manifest was deleted or never committed — do not re-run the CLAUDE.md/AGENTS.md migration logic in Step 5 (it is not idempotent against an already-migrated file). Instead: inspect `docs/ai/rules/` for the owned files already present, reconstruct the stack subscription from which `docs/ai/rules/stacks/<name>/` directories exist, reconstruct `ownedFiles` from the files actually on disk under `docs/ai/rules/` plus `opencode.json` if present, default `keep` to `[]` (there is no manifest to carry it from), ask the user to confirm the reconstructed stack list, then proceed as upgrade mode from Step 3 onward (skip Step 5 entirely).

## Step 2 — Determine the stack subscription

- **Upgrade mode:** use `stacks` from the existing manifest (legacy `profiles` key reads as the same field). Do not ask again — unless the user's request explicitly asks to add or drop a stack (e.g. "we added an Aurelia frontend, pick that up"). In that case, re-run the stack-signal detection below, present the updated candidate list alongside the existing subscription, and ask the user to confirm the new list. Store the confirmed list as the new `stacks`; Step 3.5's deletion logic then removes any stack's owned files that are no longer in the confirmed list, exactly as it does for an edited/removed core rule.
- **Fresh scaffold / legacy migration:** inspect the repo for stack signals — any `*.slnx`/`*.sln`/`*.csproj` file → candidate stack `dotnet`; an `aurelia` entry in `package.json` dependencies, or an `aurelia_project/aurelia.json` file (Aurelia v1 convention) → candidate stack `aurelia`. Present the detected candidates to the user and ask them to confirm or adjust before proceeding. Store the confirmed list as `stacks`.

## Step 3 — Apply owned files

Owned files live in this skill package at `assets/rules/`. For each file:

1. Always copy every file under `assets/rules/core/` to `docs/ai/rules/core/` in the target repo, preserving relative path, using a byte-for-byte Bash copy (`cp`) — never the Write or Edit tools, and never retype or reformat the content. Also copy the owned wiring file `opencode.json.tpl` (from `assets/templates/`) to the target repo root as `opencode.json`, and the engine `assets/engine/engine.py` to `docs/ai/engine.py` (both byte-for-byte `cp`; neither has placeholders — owned, machine-managed files refreshed every run). (The legislator-hooks write-guard blocks Edit/Write on `docs/ai/rules/**`, `docs/ai/engine.py` and `opencode.json` in legislated repos; the Bash copy is the sanctioned path.)
2. For each confirmed stack name in `stacks`, copy `assets/rules/stacks/<name>/` to `docs/ai/rules/stacks/<name>/` the same way.
3. Read `VERSION` (a single integer) — this is the `legislatorVersion` to write into the manifest.
4. Compute the new `ownedFiles` list: every path just copied — the `docs/ai/rules/**` files, `docs/ai/engine.py`, and the root `opencode.json` — expressed relative to the target repo root (e.g. `docs/ai/rules/core/okf.md`, `docs/ai/engine.py`, `opencode.json`).
5. **Deletions:** compare the new `ownedFiles` list against the "old" `ownedFiles` list — the existing manifest's list in upgrade mode, or the reconstructed list from Step 1's edge-case guard when there was no manifest to read. If the old list contains a path not present in the new list, delete that file from the target repo (it was removed from the constitution, or its stack was de-selected in Step 2). If deleting a file empties its containing `docs/ai/rules/stacks/<stack>/` directory, remove the now-empty directory too.
6. **Keep list — protected project artifacts.** Carry forward the existing manifest's `keep` list (default to `[]` when the key is absent — older manifests predate it). Then apply any keep requests in the user's prompt: **adding** requires the path to exist in the repo (if it doesn't, skip it and report the refusal in Step 7) and to not be an owned file — anything in the manifest's `ownedFiles`, which since v20 means `docs/ai/rules/**`, `docs/ai/engine.py` and the root `opencode.json` (owned files are machine-managed, not keepable; the file-authority table gives them `replace`, and a kept path is `link-only` — a file cannot be both) — nor a generated artifact (`docs/ai/baseline.md`): a machine rewrites it wholesale, so a keep promise on it is unkeepable by construction; entries dedupe by path — re-marking an already-kept path replaces its reason. **Remove** an entry only when the user explicitly asks. Never add or remove keep entries on your own initiative. Kept files are project-owned content — the keep list is manifest metadata about them; it changes nothing about how this run treats the file (authority: kept paths × upgrade). Its meaning is downstream: audit check 10 verifies kept files stay wired into the layer, and any future restructuring must leave kept paths in place.
7. Write `docs/ai/manifest.json` with this exact serialization — 2-space indentation, keys in this order (`legislatorVersion`, `stacks`, `keep`, `ownedFiles`), `stacks` as a single-line inline array (e.g. `["dotnet"]` or `["dotnet", "aurelia"]` — never expanded across multiple lines, regardless of how many entries it has), `keep` written as `[]` on the same line as its key when empty and otherwise one entry per line sorted by `path`, each entry a single-line inline object with keys in the order `path`, `reason`, and `ownedFiles` sorted with each entry on its own line as shown below — so that two runs with no actual change produce a byte-identical file and no spurious diff:

```json
{
  "legislatorVersion": <int from VERSION>,
  "stacks": [<confirmed stack names>],
  "keep": [
    {"path": "<repo-relative path>", "reason": "<why this artifact must stay as-is>"}
  ],
  "ownedFiles": [<new ownedFiles list, sorted>]
}
```

With no kept files that line is exactly `  "keep": [],` — never an expanded empty array.

**Ensure the v14 file model (every mode, including upgrade):** `AGENTS.md` is the canonical entry document and `CLAUDE.md` is a symlink to it. If a real (non-symlink) `CLAUDE.md` exists and `AGENTS.md` does not, rename `CLAUDE.md` → `AGENTS.md` (`git mv` if tracked, else Bash `mv`) — the renamed file becomes canonical with its existing content. Then ensure `CLAUDE.md` is a symlink → `AGENTS.md`: create it with Bash `ln -s AGENTS.md CLAUDE.md` when absent; if a real `CLAUDE.md` still lingers (only possible when `AGENTS.md` already existed and the rename was skipped), replace that real file with the symlink. In fresh-scaffold mode `AGENTS.md` is written from `AGENTS.md.tpl` (Step 4) and the symlink created alongside. The `opencode.json` copy in step 1 above completes the v14 model. (Audit mode is read-only and performs none of this — it reports staleness instead.)

## File authority

This table is the only statement of what an invocation mode may do to a file in the target repo. Every other mention of a right in this skill is a reference to a cell, written `(authority: <class> × <mode>)`; a right stated anywhere else in prose is a defect the static check rejects.

| artifact class | installing | installing | maintaining | maintaining | inspecting |
| | scaffold | migrate | upgrade | restructure | audit |
|---|---|---|---|---|---|
| entry document (`AGENTS.md`; `CLAUDE.md` is its symlink) | replace | lossless-write | propose-only | lossless-write | read-only |
| owned law (`docs/ai/rules/**`, `docs/ai/engine.py`, `opencode.json`) | replace | replace | replace | never-touch | read-only |
| manifest (`docs/ai/manifest.json`) | replace | replace | replace | never-touch | read-only |
| project rules (`.claude/rules/**`) | create-if-absent | lossless-write | create-if-absent | move-or-merge | read-only |
| scaffolded artifacts (Step 4's table, the OKF bundle included) | create-if-absent | create-if-absent | create-if-absent | move-or-merge | read-only |
| relocated owner content (glossary rows, the OKF mapping table, legacy plans/specs, `BL-NNN` directories) | read-only | lossless-write | read-only | move-or-merge | read-only |
| foreign structures (`.cursorrules`, stray rulebooks, non-standard AI dirs) | read-only | read-only | read-only | move-or-merge | read-only |
| kept paths (manifest `keep`) | link-only | link-only | link-only | link-only | read-only |

**State rule.** `docs/ai/manifest.json` is the boundary: absent, the layer is being *installed*; present, it is being *maintained* or *inspected*. A mode's column is fixed; its state header names the repo state the mode assumes. Harvest is a report section of migrate, upgrade and audit and writes nothing; steward is a human duty performed on the skill's own repository. Neither acts on a legislated repo, so neither has a column.

**Vocabulary (closed).**

- `replace` — the content comes whole from the skill; whatever exists is replaced byte-for-byte (Bash `cp`), never merged, never edited. The manifest is the one `replace` artifact the skill *generates* rather than copies: `keep` is carried forward and `ownedFiles` recomputed (Step 3) — regeneration from the skill's own inputs, not a merge of owner content.
- `create-if-absent` — created from a template when missing; an existing file is left as it is, whatever its content.
- `lossless-write` — the run writes owner content (into the file, or out of it into its home) such that every sentence survives; the fidelity pass is the proof. Removing machine wiring that points at nothing (a dangling `@import`, a stale map row) is inside this right — such a line is not owner content.
- `propose-only` — the content is never written; exact lines are printed in the report under `## Needs your review`, and the owner applies them. The file-model canonicalization of Step 3 (rename `CLAUDE.md` → `AGENTS.md`, symlink back; bytes identical) is wiring, not a write, and is inside this right — the document's content before and after the run is byte-equal.
- `move-or-merge` — relocated or folded whole under an approved plan item (`references/restructure.md` §2); content is carried, not edited.
- `link-only` — a link *to* the path may be added elsewhere; the path itself is not moved, merged, fixed, or rewritten.
- `read-only` — read to judge and report; zero writes.
- `never-touch` — the mode has no authority of its **own** over the file: it never hand-edits it and never decision-gates it. This is **not** "report it and stop". Where the mode's action set delegates the repair to another column, the run performs that repair itself, in the same run, under the delegated column's rights — restructure's `heal` runs SKILL.md Steps 2–3 as-is over the classes whose cell references `references/restructure.md` §2's heal bullet carries, and that delegated run is the only way those files change while restructure is executing. A mode whose action set delegates nothing for the class simply leaves it alone.

## Step 5 — Legacy migration (migration mode only)

Follow `references/migration.md` in full. Summary of what it covers:

1. Canonicalize the entry document first: if the repo has a real `CLAUDE.md` (pre-v14) and no `AGENTS.md`, rename `CLAUDE.md` → `AGENTS.md` (`git mv` if tracked, else Bash `mv`) — the renamed file becomes canonical. If `AGENTS.md` already exists, it stays canonical. If BOTH exist as real files, stop and ask which is canonical (decision gate — never silently overwrite the loser). Then ensure `CLAUDE.md` exists as a symlink → `AGENTS.md` (create via Bash `ln -s`; if a real `CLAUDE.md` lingered it was just renamed away). Split the canonical `AGENTS.md` three ways: law-shaped project rules (carved into `.claude/rules/<topic>.md` per §1), project-specific instance data (kept in `AGENTS.md`), and content now covered by an owned rule (removed, replaced by the full `AGENTS.md.tpl` v2 wiring: the `@docs/ai/rules/...` import block, the `@docs/okf/codebase-map.md` import, the `## Boundaries` section, and the glossary pointer line — see `references/migration.md` §1; migration writes these directly rather than proposing them in Step 7). `opencode.json` is written by Step 3 as usual.
2. Extract any existing "what maps to what" / category table from the old AGENTS.md (or pre-v14 CLAUDE.md). If `docs/okf/index.md` already exists and already has an equivalent table, leave it untouched — do not write `docs/okf/index.md` at all. Otherwise, derive `{{PROJECT_NAME}}`, `{{PROJECT_OVERVIEW}}`, `{{STACK_SUMMARY}}` from the old AGENTS.md/CLAUDE.md and the extracted table as `{{CATEGORY_MAPPING_TABLE}}`, then hand these four values to Step 4 — Step 4 is the only step that actually writes `docs/okf/index.md` from `okf-index.md.tpl`; this step only supplies its placeholder values.
3. Relocate any plans/specs directory outside the standard location (e.g. `.claude/plans/`) into `docs/superpowers/plans/` (create the directory as part of the relocation; it is no longer pre-created empty — new work is born in `docs/cases/BL-NNN/` per `core/sdd.md`), fixing any relative references inside the moved files.
4. Remove `docs/superpowers/` (or equivalent) from `.gitignore` if present.
5. If an existing AGENTS.md (or pre-v14 CLAUDE.md) section conflicts with an owned rule (e.g. contradictory branch-naming convention), do not resolve it — surface the conflict and ask, per the decision-gate rule.

Run this step before scaffolding `docs/okf/index.md` in Step 4 — Step 4's `docs/okf/index.md` row depends on the project-name/overview/stack-summary/category-table values this step derives.

## Step 6 — Verify

1. For every file in the new `ownedFiles` list, diff it against the corresponding `assets/rules/...` source file (e.g. `diff docs/ai/rules/core/okf.md <skill-path>/assets/rules/core/okf.md`) — must be byte-identical. If any diff is non-empty, re-copy and check again; if it still fails, stop and report the failure instead of continuing.
2. Confirm every artifact from Step 4's table exists (or was already present).

## Step 7 — Report

**Report skeleton (pinned).** The report's title is a single `#` line; every section of the report is a `##` heading — `Created`, `Overwritten`, `Deleted`, `Needs your review`, `Keep list`, `Constitution candidates`, `Health`. Section headings are byte-for-byte: that level and that text, wherever the report appears (chat or a saved copy). No report section nests below `##`.

Print a summary with these sections: **Created** (new files/directories), **Overwritten** (owned files updated by this run), **Deleted** (owned files removed because they left the constitution or a de-selected stack), **Needs your review** (authority: entry document × upgrade = propose-only — exact lines are proposed here for the user to apply themselves, e.g. an `@import` line to add/remove when a rule file was added/removed, and, when this run scaffolded an artifact an existing `AGENTS.md` doesn't reference yet, the wiring for it: the `@docs/okf/codebase-map.md` import, a `## Boundaries` section, the glossary pointer line. `CLAUDE.md` is a managed symlink to `AGENTS.md`, never project prose). Additionally, only when this run changed the `keep` list or refused a keep request, include a section headed exactly `## Keep list`: each entry added or removed (path + reason) and each refused request with why it was refused (the path does not exist, or the path is an owned file — any entry of the manifest's `ownedFiles`).

In **upgrade mode only**, append a final section, `## Health`, running the cheap audit checks (1–6 in the Audit section below) against the post-run state: list findings in the Audit section's line format; if there are none, print exactly `Health: clean`. Fresh-scaffold and migration runs skip this section — everything they just created is definitionally fresh.

In **migration and upgrade modes** (never fresh scaffold — everything there was just written by this skill), also scan project-owned prose for **constitution candidates** and, when at least one qualifies, append a section headed exactly `## Constitution candidates` — that heading level and text, byte-for-byte, wherever the report appears (chat or a saved copy) — after the Keep list section, before Health (when those sections are absent, make it the report's last section):

```
## Constitution candidates
- "<verbatim quote>" — <repo-relative path>
```

A candidate is a statement passing all three tests: (1) **law-shaped** — imperative and diff-checkable ("always …", "never …", "must …", "… before every commit"), not description or narration; (2) **not already covered** — no rule under `docs/ai/rules/**` states it (judge by meaning, not wording); a statement *contradicting* an owned rule counts as covered by that rule — it is decision-gate material, never a candidate; (3) **generalizable** — it would make sense verbatim in another repo of the same stack. Project-instance data is an instantiation of law, not law: a concrete path, this project's branch pattern, a named contact or environment stays put and is never proposed. Scan the entry document's project-specific sections — `AGENTS.md`, or a pre-v14 real `CLAUDE.md` when `AGENTS.md` does not exist, which is the state audit mode finds a pre-v14 repo in, since audit performs no canonicalization (skip the `@import` block and the template wiring lines), every `.md` under `.claude/rules/`, prose under `docs/okf/`, and every stray rulebook found by audit check 12's scan (run that scan in every mode that harvests); do not scan `docs/ai/rules/**`, `docs/adr/**`, `docs/journal/**`, `docs/backlog.md`, `docs/cases/**`, or `docs/superpowers/**` — except a stray rulebook the check-12 scan found there. Skip any line carrying `<!-- legislator: not-law -->` on it or as the entire immediately preceding line — the user has already ruled that statement out. Skipping is silent: never quote, list, or otherwise mention a suppressed statement anywhere in the report — mentioning it re-surfaces exactly what the user silenced. **This binds every section of every report, not only the candidates section, and it forbids reporting your own compliance:** a note that a statement carries the marker and was correctly excluded quotes the statement and names the file, which is the very disclosure the marker exists to prevent. There is no diligence to demonstrate here — the correct evidence of obedience is silence. **The scan is per source and exhaustive:** take the sources listed above one at a time and judge every statement in each — finding a candidate in one source never ends the pass, and no source is skipped because an earlier one already yielded something. Count the sources you scanned against the sources named above before writing the section. Candidates are **proposals only**: never write them to any file; the user promotes worthy ones into the skill's central `assets/rules/**` (bumping VERSION) and re-runs `/legislator` fleet-wide. If nothing qualifies, omit the section entirely.

Do not run `git add` or `git commit`. The user reviews and commits.

## Audit — read-only health check

Run this section INSTEAD of Steps 0–7 when the user asks to audit or health-check the AI layer. It performs **zero writes**: record `git status --porcelain` and `git rev-parse HEAD` before starting, and verify both are byte-identical after producing the report — if either changed, the run has a bug; say so explicitly in the report.

Perform these checks (severity in parentheses; a finding names the offending path, date, or entry verbatim):

In findings, `[check-name]` is the check's pinned slug — use exactly these: 1 `imports-resolve`, 2 `unresolved-placeholders`, 3 `owned-integrity`, 4 `staleness`, 5 `okf-index-links`, 6 `codebase-map`, 7 `orphan-docs`, 8 `journal-recency`, 9 `foreign-structures`, 10 `keep-list`, 11 `project-rules`, 12 `stray-rulebooks`, 13 `glossary-vitality`, 14 `skill-bindings`, 15 `okf-anchors`, 16 `legacy-home-violation`, 17 `okf-sync-debt`.

**Execution split (v23).** The mechanical checks — every check except 11 and 12 — are executed by the engine, and the engine prints the report. The model's part is exactly three things: (1) perform checks 11 and 12 and the constitution-candidates scan (the semantic judgements below); (2) write them to a temp JSON file — the model-findings channel: `{"findings": [{"check": "<slug>", "severity": "Critical|Warning|Info", "line": "<the full finding line in the pinned format>", "escalates": "<optional: the path of an engine Info entry this finding supersedes>"}], "candidates": ["- \"<verbatim quote>\" — <repo-relative path>"], "verification": "<optional final line: the zero-writes attestation>"}`; (3) run the **skill package's own engine** — `python3 <skill-path>/assets/engine/engine.py audit --root . --skill <skill-path> --model-findings <that file>` from the repo root — and deliver its stdout **verbatim** as the report: no modification, no re-composition. Always the skill's copy, never the repo's delivered one: audit is the skill's mode, and a repo mid-upgrade may carry an older engine (or none at all, below v20) that does not know this job. Read the exit code: 0 and 1 mean the report was printed (clean / with findings); any other exit is the engine failing — report that failure, never a clean audit. The check definitions below remain the law of what each check means; the engine is their executor.

1. **Imports resolve (Critical):** every `@<path>` line in AGENTS.md (the canonical file; `CLAUDE.md` is a symlink to it) points to an existing file.
2. **Unresolved placeholders (Critical):** no `{{TOKEN}}` pattern in AGENTS.md, any `.md` under `docs/`, or any `.md` under `.claude/rules/`, except `docs/adr/template.md` (its tokens are intentional). A token inside an inline-code span (backticks) or a fenced code block is a **quotation** — prose about the templating system, not an artifact awaiting a fill — and is never a finding; only a token standing bare in the text is unresolved. (Any repository that documents a templating system quotes tokens; before this rule, this repository alone carried fourteen false Criticals.)
3. **Owned-layer integrity (Critical):** `docs/ai/manifest.json` parses; every `ownedFiles` entry exists on disk; every owned file is byte-identical to its source — `docs/ai/rules/**` files against `<skill-path>/assets/rules/...`, `docs/ai/engine.py` against `<skill-path>/assets/engine/engine.py`, and `opencode.json` against `<skill-path>/assets/templates/opencode.json.tpl` (diff each one).
4. **Constitution staleness (Info):** manifest `legislatorVersion` vs. `<skill-path>/VERSION`; if behind, note "re-run /legislator to upgrade".
5. **OKF index links (Warning):** every markdown link in `docs/okf/index.md` resolves to an existing file.
6. **Codebase-map freshness (Warning):** skip if `docs/okf/codebase-map.md` is absent. Otherwise: every directory named in the map's table exists, and every non-generated top-level directory (ignore hidden directories and `bin/`, `obj/`, `node_modules/`, `dist/`) has a row.
7. **Orphan docs (Warning):** an `.md` under `docs/okf/` or directly in `docs/` that no other `.md` file (or AGENTS.md) **references**. A file counts as referenced when any other markdown file mentions it by markdown link, by `@import`, or by inline-code path mention — its repo-relative path (or a relative path resolving to it) inside backticks; rule text naming `docs/okf/index.md` in backticks wires that file in. Exempt by directory convention: `docs/ai/rules/**`, `docs/adr/**`, `docs/journal/**`, `docs/superpowers/**`, `docs/cases/**`, and `docs/backlog.md`.

A real (non-symlink) `CLAUDE.md` sitting alongside an `AGENTS.md` in a current-manifest repo is reported here at **Warning** — it should be the symlink to `AGENTS.md`. When a listed file's content is predominantly law-shaped (check 12's test), report it here at **Warning** instead of Info — a foreign config full of law is unloaded law, not mere leftovers. 10. **Keep-list integrity (Warning):** for every entry in the manifest's `keep` list: (a) the kept path exists on disk — otherwise finding `<path>: kept path missing from disk → restore it or remove the keep entry`; (b) the kept file is referenced from somewhere — same definition as check 7, searched across AGENTS.md and every `.md` in the repo, with no directory exemptions, except that kept files under `.claude/rules/**` are exempt from (b) entirely (auto-loading is their wiring) — otherwise finding `<path>: kept but referenced from nowhere → link it from docs/okf/index.md or AGENTS.md`. If the manifest has no `keep` key at all, add to the **Info** section exactly `- [keep-list] docs/ai/manifest.json: no keep key (pre-keep-schema manifest) → re-run /legislator to refresh` and skip the check.
11. **Project-rules integrity (Warning):** every `.md` under `.claude/rules/` is project law (see `core/project-rules.md`). Flag any statement there that contradicts an owned rule under `docs/ai/rules/` — finding `<path>: contradicts <owned rule path> → align it with the owned rule, or record an explicit exception in the file (conflicts are decision-gate material; never silently pick a side)`. Scan AGENTS.md's project-specific prose (skip the `@import` block and template wiring lines) the same way — an AGENTS.md statement contradicting an owned rule is the same finding shape with `AGENTS.md` as the path; this scan runs even when `.claude/rules/` is absent. For the `.claude/rules/` part, skip when the directory is absent — but when it is absent while the manifest's `legislatorVersion` is current (check 4 clean), add to the **Info** section exactly `- [project-rules] .claude/rules/: directory absent (git does not track empty directories) → mkdir it so project rules have their home`.
12. **Stray rulebooks (Warning):** an `.md` file whose content is predominantly law-shaped rule or checklist items (imperative, diff-checkable — the same law-shaped test as the constitution-candidates scan) that is not wired into the AI layer. A file is exempt when AGENTS.md, any `.md` under `.claude/rules/`, or `docs/okf/index.md` references it (check 7's referenced definition, restricted to those referrers — the surfaces sessions actually load, the OKF index via `core/okf.md`); kept paths (manifest `keep` list) are exempt — the keep entry is the user's ruling that the document stays as-is. ## Restructure — approval-gated repair

Run this section INSTEAD of Steps 1–7 when the user asks to restructure, repair, or reorganize the AI layer — but run Step 0's preconditions first: restructure writes, and a dirty working tree would mix the user's changes into the applied diff. Detailed mechanics live in `references/restructure.md` — read it before proposing. The protocol is strict: **diagnose → propose → approve → apply**, with a hard stop at approve.

1. **Diagnose (zero writes):** run the Audit section in full. The plan is built from its findings.
2. **Propose (still zero writes):** print a plan headed exactly `# AI-Layer Restructure Plan — <repo name>, <ISO date>`, then numbered items, one line each: `N. [action] <current> → <target>: <one-line what/why>` — except `decision` items, whose shape is `N. [decision] <where> ↔ <owned rule>: <one-line conflict>`. `[action]` is one of the closed set — `move`, `merge`, `link`, `fix`, `heal`, `decision` — defined in `references/restructure.md`. Anything conflicting with an owned rule, and any call this skill cannot make alone, is a `decision` item — including any proposal to delete **content that is not being carried anywhere** (a dead or orphaned file: deleting it exists only as a `[decision]` item, executed by the owner's hands, never by the run). Deleting a **merge source whose every line the fidelity pass has verified** is part of `merge` itself, not a deletion decision. **A dangling `@import` of a nonexistent file is always a `fix`, never a `decision`** — removing a dead line from AGENTS.md (or anywhere) is within the skill's authority — a dangling `@import` is machine wiring, not owner content (authority: entry document × restructure = lossless-write). **Agent-tooling scratch debris (check 9's working-dir debris class — `.superpowers/`, `.specify/`, scratch diff/report dumps) is never a `move` or `merge` source:** its content is tool exhaust, not project content to carry — folding it into the journal, the OKF or anywhere else invents project content, which the closed `fix` scope already forbids; the only lawful plan item for it is a `[decision]` (delete it, or declare it kept), executed by the owner. **A case-shaped `BL-NNN` directory outside `docs/cases/` is always a `move`, never a `decision`** — §1's cases row pins its home and outranks the legacy homes, and age is not ambiguity: the legacy-home rule for plans and specs covers only artifacts that are *not* inside a `BL-NNN` directory. **The scope of `fix` is closed:** it repairs wiring and derived artifacts only — dangling imports/links, unresolved tokens, stale map rows, glossary seeding, the v14 file-model rename. It NEVER deletes or rewrites law-bearing content: a statement contradicting an owned rule is a `[decision]` whatever file it lives in — removing it "as a fix" is auto-resolution by another name and is forbidden. Findings that would require inventing project content (e.g. a missing journal entry) are never plan items — list them at the end under a section headed exactly `## For the team:` (that heading level and text, byte-for-byte) instead. **A finding carried into that section keeps the pinned slug the Audit section gives it** — `[okf-anchors]`, not `[check-15]`. There is one finding namespace in this skill and it is that list; writing check numbers here creates a second one, which is how a report stops being machine-readable without anyone noticing. **Check-11 (`project-rules`) findings are always `[decision]` items, one per contradicting file** — a project rule contradicting an owned rule is the archetypal call this run cannot make alone: each item names its file and both sides of the contradiction, that file stays byte-unchanged (the closed `fix` scope already forbids rewriting law-bearing content), and no finding is dropped merely because no other plan item touches its file. Check 11 scans **two** surfaces — every `.md` under `.claude/rules/` **and** the entry document's own prose — so raising an item for one surface never discharges the other: count the check's findings and count your `[decision]` items, and if the second number is smaller you have dropped one. Check-14 (`skill-bindings`) findings are likewise never plan items — they describe this machine's skill installation, not the repo; list them under the `## For the team:` section with the README's setup pointer — **and never apply them yourself: editing `.claude/rules/skills.md` to add or remove sanctioned skills is the repo owner's call, not this run's.** **Check-15 (`okf-anchors`) and check-17 (`okf-sync-debt`) findings are likewise never plan items** — a document naming code that is gone is owner prose, and rewriting it is inventing project content, which the closed `fix` scope already forbids; list them under the `## For the team:` section with the engine command that reproduces them, and leave every named document byte-unchanged. Close the plan with `Kept (immovable): <path> — <reason>` for every manifest `keep` entry (`Kept (immovable): none` when the list is empty). A kept path must never be the source of a `move`, `merge`, or `fix`; a kept path is link-only (authority: kept paths × restructure).
3. **Approve — hard stop:** apply nothing until the user approves, item-by-item or all at once. Blanket approval still excludes every `decision` item: ask each one individually; unanswered ones stay open, change nothing, and are re-surfaced by every future run.
4. **Apply + verify:** execute the approved items per `references/restructure.md`, then run the **fidelity pass**: every content line of every file this run moved or merged must still be greppable somewhere in the repo (deletions that are an approved `fix` item's stated purpose — a dangling import line, a stale map row, a dead link — are exempt: removing them IS the item; merge sources stay alive until the pass verifies every line, then are deleted as the phase's last act). If applying an item would otherwise lose a line, do not apply it. Print the final report: the plan repeated **verbatim — each item exactly as printed above, `[decision]` items included with their `<where> ↔ <owned rule>` line** — with an outcome appended to each item (`— applied`, `— skipped`, `— blocked: <why>`, `— decision: open`), then exactly `Fidelity: verified (<N> lines tracked)` — or an explicit failure line naming what was lost and where it came from. Do not commit. A repo already in standard shape yields a plan with no numbered items (open `decision` items excepted) and zero writes.
