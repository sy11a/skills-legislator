## changelog

- `legislator sdd-lint` no longer reddens a branch on every other case's pending fragment: a branch that names a case answers only about that case's own fragment — reported by name when it is absent — and a branch naming no case reports no finding at all ([BL-441](docs/cases/BL-441-fragment-lint-reads-its-own-case/spec.md)).

## journal

- Inverted the branch check rather than tightening it. The old reading was "every fragment must belong to this branch"; the law means "this branch's case has a fragment" (`core/changelog.md`: one fragment per case, a task branch adds one). Turning it around means resolving the branch's case key — verbatim (`bl/BL-347-verbatim`) or slashed (`bl/347-retelling-layer`, `l/3-change-fragments`) — with `BranchMatchesCase` kept as the judging primitive, and answering only that case.
- Dead end avoided: deriving the key naively from any `<letters>-<digits>` run treats `release/3` as carrying case `release-3`, which is the exact false-finding class being removed. Settled (issue #51's open question) by a `non_case_branch_prefixes` option (`release`, `hotfix`, `rc`): a leading integration prefix names a release, not a case. "Presence" is the file's name, not its shape — a malformed fragment is reported by the shape checks, not as an absent one.
- Rework after the refutation round: the `non_case_branch_prefixes` blacklist above was refuted — it minted false keys on `rc/edition-27` and any `feature/<word>-<digits>` name, and an open blacklist cannot enumerate the fleet's non-case vocabulary. Replaced by the law's closed set (`case_branch_prefixes` = `bl`, `l`): a branch names a case only when its ticket's letters are a case prefix. The ticket is read from the last name segment, and the missing-fragment finding reports the law's key form (`BL-NNN`).
